# F22b — Toolchain portátil, launcher y paquetes

- **Fecha**: 2026-11-01
- **Estado al cerrar**: ✅ hecha en lo que se puede probar sin el usuario: el toolchain portátil de
  Windows compila el proyecto y pasa los tests en la CI, el launcher funciona, las etapas se
  compilan en dos niveles y la release se arma y se revisa sola. **Pendiente del usuario** (el
  criterio de hecho): el camino entero del ISO al juego con el ZIP en su Windows, y el Flatpak en
  Linux o en la Steam Deck. F21b sigue en paralelo.

## Hecho

### 1. Las etapas en dos niveles (`-O0` primero, después optimizadas)

- **`setup.py stages --level both|quick|optimized`** (por defecto `both`): primero compila todas
  las etapas a `-O0` y las instala como `stage_<s>-O0.<ext>`; después las compila optimizadas
  (`stage_<s>.<ext>`) y borra la rápida. Si no puede borrarla, porque un juego en marcha la tiene
  cargada (Windows), la borra la siguiente corrida.
- El nivel lo decide una variable nueva, **`MPO_OVERLAY_OPT_LEVEL`**, que solo afecta a las
  librerías de etapa: `mpo_boot` y sus corpus se quedan con `PSPRECOMP_GENERATED_OPT_LEVEL`.
  `setup.py` reconfigura con el nivel de cada pasada. Con MSVC, `0` agrega `/Od`.
- La clave de `state.json` ya incluía el nivel (`runtime_key`). La pasada rápida va en
  `stages_quick` y la optimizada sigue en `stages`, así que un `state.json` de F22 sigue valiendo.
- **`OverlayManager`**:
  - cada librería dice su nivel con un export opcional, `mpo_overlay_opt_level`. Las de antes no
    lo tienen y cuentan como `-O2`, así que siguen cargando;
  - cuando dos corpus describen el mismo PRX en la misma base, se instala el más optimizado;
  - vuelve a mirar la carpeta **en cada carga de etapa**, no solo cuando no hay corpus. Así, la
    librería optimizada se usa en la siguiente carga de la etapa, sin reiniciar el juego.
- `setup.py` también tiene:
  - **un candado por carpeta** (`setup.lock`, con `fcntl` o `msvcrt`, que se suelta solo si el
    proceso muere): nunca corren a la vez dos `install` o `stages`;
  - **`<data>/stop-stages`**: `stages` para después de la etapa en curso (es el botón Stop del
    launcher);
  - `import-save` y `export-save`, que llaman a `mpo` con el disco instalado (F18c).

### 2. Windows: llvm-mingw portátil

- **`setup.py toolchain`** baja lo que fija `profiles/mpo/config/toolchain.toml`: llvm-mingw
  20261020 (UCRT), CMake 4.4.5 y Ninja 1.13.2. Comprueba tamaño y SHA-256 antes de descomprimir y
  rechaza rutas peligrosas en el ZIP. Con `--json` imprime las rutas (la CI las usa).
  - `install` lo corre primero en Windows (`--toolchain auto`).
  - Los SHA-256 son los digests de las releases de GitHub. El del Python embebible 3.14.10 se
    comprobó contra la API de python.org.
- Para que el proyecto compile con llvm-mingw (`profiles/mpo/host/hle/CMakeLists.txt`):
  - `mpo_boot` exporta con `-Wl,--export-all-symbols`;
  - las librerías de etapa importan los datos del runtime con `dllimport` (antes solo con MSVC).
- **libc++ y `std::max`**: `framework/psprecomp/include/psprecomp/allegrex_context.hpp` usa
  `std::max` sin `#include <algorithm>`; libstdc++ y la STL de MSVC lo traen de rebote, libc++ no.
  El `CMakeLists.txt` raíz fuerza `-include algorithm` **solo con libc++** (lo detecta con
  `_LIBCPP_VERSION`). No se tocó el header, porque eso recompilaría todo el corpus del build de
  F21b del usuario (la trampa de F21). El test anidado del framework
  (`psprecomp_runtime_contract_tests`) lo recibe por `CXXFLAGS` en la CI.
- **Job de CI `windows-llvm-mingw`**: `setup.py toolchain`, configurar con
  `MPO_WARNINGS_AS_ERRORS=ON`, compilar todo y `ctest`.
- **FFmpeg** (decidido): la release de Windows lo trae **ya compilado**. Lo compila la CI de
  release de forma cruzada desde Linux con el mismo llvm-mingw (`packaging/ffmpeg`,
  `cmake/toolchains/llvm-mingw.cmake`).
  - `ffmpeg.cmake` tiene ahora un modo **`prebuilt`** (`MPO_FFMPEG_ROOT`), que `setup.py` elige
    solo en Windows cuando encuentra `ffmpeg/` junto al código. También sabe compilar de forma
    cruzada para MinGW, con `--enable-w32threads` y enlazando `bcrypt`.
  - La release lleva su tarball de código y un `BUILD.txt` con la línea de `configure` (LGPL).

### 3. El launcher (`profiles/mpo/launcher`)

- En **C++ con SDL3 y Dear ImGui 1.93.0** (decidido por el usuario). `third_party/imgui` lo baja
  al configurar con su SHA-256. `setup.py` lo apaga en el build del jugador
  (`MPO_BUILD_LAUNCHER=OFF`).
- `mpo_launcher_core` (sin SDL, con su test) lee `status --json` (con un parser de JSON mínimo) y
  las líneas `setup: <paso>: … (i/n …)`, encuentra `setup.py` y el Python según cómo esté
  instalado (el ZIP, el Flatpak o el árbol) y lista carpetas para el navegador propio.
- `mpo_launcher`:
  - elige el ISO y las fuentes con un navegador que se maneja con el mouse, el teclado o el mando
    (`ImGuiConfigFlags_NavEnableGamepad`);
  - corre Install mostrando el paso, el progreso y el log;
  - tiene Play; después de instalar, compila las etapas en segundo plano con una barra de
    progreso y Stop;
  - importa y exporta saves;
  - si algo falla, muestra las últimas líneas;
  - lanza los procesos con `SDL_Process` (lectura sin bloqueo).
- `--screenshot <bmp>` guarda la ventana y sale (con `SDL_VIDEO_DRIVER=offscreen`): es la
  evidencia de esta nota.

### 4. La release

- **`packaging/make_release.py`**:
  - **`source`**: los archivos versionados, sin `framework/psprecomp/profiles/`. El perfil de
    ejemplo de upstream trae **109 MB de código generado de otro juego** y binarios de FFmpeg, y
    nunca puede salir en una release del port.
  - **`windows`**: el ZIP con el launcher, el Python embebible (comprobado contra su pin), el
    código, FFmpeg con su código y `packaging/windows/README.txt`.
  - **`check`**: busca archivos del juego por la ruta y por el contenido (`~PSP`, ELF de MIPS,
    ISO 9660, PBP, PSF), también dentro de los ZIP anidados.
- `packaging/fetch_pinned.py` baja una entrada de `toolchain.toml` con su SHA-256. La CI de
  release la usa para el llvm-mingw de Linux y el Python.
- **`.github/workflows/release.yml`** (tag `v*` o a mano):
  - FFmpeg cruzado;
  - el launcher con el toolchain portátil;
  - el paquete con el `check` y los SHA-256;
  - el Flatpak;
  - y, con un tag, un **borrador** de release.
- **Flatpak** (`packaging/flatpak`): sobre el runtime `org.freedesktop.Sdk` 25.08, para compilar
  dentro del sandbox. Trae el launcher y el código. Los permisos están en
  `docs/analysis/distribution.md` §3.

### 5. `--unimplemented` (decidido)

`setup.py play` deja **`stop`**, la regla de `CLAUDE.md` §5. Los 15 imports sin implementar no
tuvieron ninguna llamada en los cuatro tramos de F21. Si un jugador llega a uno, el juego se
detiene con el nombre del NID y el launcher muestra las últimas líneas. `continue` devolvería 0 en
silencio.

## Evidencia de los criterios de hecho

- **Las etapas a `-O0` son correctas** [V]: la repetición completa de `analysis/f21/tramo1.input`
  (512 s de juego: `init`, `r_main01`, `title`, `briefing` y la misión `st03t1`), sin ventana y con
  softgpu, con las cinco etapas compiladas a `-O0` por `setup.py stages --level quick`: `frame
  checks: 511 matched, 0 differed`, `interpreter: 0 instructions`.
- **Medición de rendimiento** (el mismo `mpo_boot`, CPU de usuario de toda la repetición):

  | Etapas | Coincide | CPU | Reloj |
  |---|---|---|---|
  | `-O0` | 511/511 | 259 s | 4 min 19 s |
  | `-O2` (las de F21) | 511/511 | 280 s (con una compilación al lado) | 4 min 39 s |
  | intérprete | **132/511**: se separa en el flip 7740, en `st03t1` | — | — |

  En este recorrido, el código de las etapas pesa poco frente a softgpu y `mgp_main`. `-O0` y
  `-O2` no se distinguen del ruido: hasta los 120 s, las tres variantes tardan lo mismo (26,4 a
  27,0 s). Lo que importa es que **el intérprete no reproduce la misión bit a bit** y `-O0` sí.
- **Tiempo de compilar a `-O0`** [V, `setup.py stages --level quick`, pool del código generado en 3,
  máquina compartida]:
  - `title` 10 s, `briefing` 13 s y `st03t1` 33 s. A `-O2`, `title` tardaba 115 s, `briefing`
    163 s y una misión parecida (`st07m1`) 410 s (F22);
  - las cinco de `tramo1`, 99 s en total;
  - **las 92 etapas: ~40 min** (87 en 38 min 28 s, más las 5 de antes en 99 s). Ninguna pasó de
    47 s. A `-O2` habían sido **6 h 45 min** con `-j5` (F21): unas 10 veces menos;
  - ojo: las librerías `-O0` ocupan **4,6 GB**, contra ~2,8 GB las optimizadas. Mientras dura la
    segunda pasada, el disco llega a ~11 GB.
- **El reemplazo por la optimizada y el Stop** [V]: `stages --level optimized --only
  title,briefing`, creando `stop-stages` mientras compila `title`:
  - `title` se instala optimizada en 142 s y su `-O0` se borra;
  - `stages` para antes de `briefing` ("stopped (asked to)") y borra el archivo de Stop;
  - `status` da 92 instaladas, 1 optimizada y 91 solo rápidas;
  - en una repetición, el juego instala `title (stage_title.so, -O2)` e `init` y `r_main01` desde
    sus `-O0`, con `59 matched, 0 differed` hasta los 60 s.
- **El `install` limpio** (scratchpad, con el `setup.py` de F22, Clang 18 y la máquina compartida
  con una CI de otro proyecto): 29 min 44 s (`generate` 66 s; `main` 1565 s).

## Decisiones tomadas

- **Launcher en C++ con SDL3 y Dear ImGui** (el usuario), no Tkinter: se maneja con el mando, y
  el Python embebible no trae Tkinter.
- **FFmpeg para Windows, precompilado por la CI** con el mismo llvm-mingw, dentro del ZIP con su
  código. Se descartó un MSYS2 portátil.
- **El Python va dentro del ZIP**, y el toolchain se baja: así, el launcher solo lanza procesos y
  toda la lógica de las descargas queda en Python, con sus tests.
- **Las etapas en dos niveles con nombres de archivo distintos**: Windows no deja reemplazar una
  DLL cargada.
- **`--unimplemented stop`** para la release, con el error a la vista en el launcher.
- **El arreglo de libc++ va por el CMake raíz, no en el header**, para no recompilar el corpus del
  build de F21b.
- **Probar Windows solo con la CI** (el usuario): el clasificador de permisos no dejó bajar y
  ejecutar llvm-mingw en esta máquina.

## Pendiente y trampas encontradas

- **El intérprete no es exacto en `st03t1`**: la repetición de `tramo1` con las etapas en el
  intérprete se separa de la grabación en el flip 7740 (con `-O0` y `-O2` coincide). Para el
  jugador importa poco, porque con la pasada rápida pasa poco tiempo en el intérprete, pero es un
  bug del intérprete o de su VFPU. Queda para F23+ (o para F21b, si aparece algo raro jugando
  antes de que la etapa esté compilada).
- **El `#include <algorithm>` en `allegrex_context.hpp`** va al fork (`Alvaro8317/PSPRecomp`,
  rama `mpo`) cuando convenga recompilar todo el corpus. Después se puede quitar el
  `-include algorithm` del `CMakeLists.txt` raíz y el `CXXFLAGS` de la CI.
- **Trampa**: el submódulo trae `profiles/vcs/generated` (código generado de otro juego). Cualquier
  paquete hecho con `git archive --recurse-submodules` lo incluiría. `make_release.py` lo deja
  fuera y el `check` lo atraparía.
- **Sin probar**:
  - el `install` entero con el toolchain portátil y el juego (solo en la máquina del usuario);
  - `mpo_boot` enlazado con llvm-mingw y el juego;
  - el Flatpak instalado en una máquina: la CI lo construye, pero aquí no hay `flatpak`;
  - el launcher en una ventana real, con el mando.
- `PSPRECOMP_GENERATED_JOBS` (1 por cada 4 GiB) también limita la pasada rápida, que usa mucha
  menos memoria. Se podría subir para `-O0`, pero no se midió.
