## Decisiones tomadas

- **Selección del perfil desde la raíz.** PSPRecomp solo busca perfiles dentro de su propio árbol
  (`framework/psprecomp/profiles/<id>`). Para no tocar el submódulo, la raíz se queda con
  `PSPRECOMP_PROFILE`: al framework le pasa `""` como variable normal y después añade
  `profiles/mpo`. Lo descartado:
  - un symlink dentro del submódulo, porque no es portable a Windows y ensucia el submódulo;
  - un fork, porque por ahora no hace falta.
- **Sin parches al framework.** Con GCC, Clang, MSVC y clang-cl compila tal como está, así que de
  momento no hay fork ni `patches/`. Si más adelante hace falta un cambio genérico (MIT), lo preferible
  es un fork en GitHub con una rama apuntada por el submódulo, porque se puede enviar como PR upstream.
- **Windows con MSVC y clang-cl** (la nota abierta de F00). El usuario lo eligió: el código generado
  choca con límites distintos en cada compilador.
- **Repo público** (lo decidió el usuario). Es open source, en línea con la GPL. Además, en el repo
  privado Actions estaba bloqueado por facturación.
- **Estilo de C++** (`CLAUDE.md` §11 lo dejaba por definir): el de `.clang-format`, parecido al de
  PSPRecomp para que el código del perfil se lea igual que el del framework.

## Pendiente y trampas encontradas

- **PSPRecomp upstream no trae los ganchos de overlays que asume `CLAUDE.md` §3.** En este commit no
  existen `set_runtime_missing_function_hook` ni `unregister_functions`, ni nada de librerías
  compartidas por overlay: `grep` en `include/` y `src/` no encuentra nada. Sí existen
  `register_function`, `register_hle`, `register_native_fast_path`, `set_runtime_post_dispatch_hook`
  y `PSPRECOMP_HLE_HISTOGRAM`.
  - Lo más probable es que esos ganchos sean del fork de Yakumo.
  - El perfil de ejemplo de upstream es **VCS** (GTA: Vice City Stories), solo para Windows con DX12.
  - **Afecta a F04, F06 y F13.** En F06 hay que revisar el fork de Yakumo y decidir si se portan esos
    ganchos como parche genérico (MIT) o se escriben.
- **Los runners `windows-latest` ya traen Visual Studio 18 2026** (MSVC 19.51), no VS 2022 como dice
  `CLAUDE.md` §3. Por ahora el CI usa el generador por defecto. Si hace falta fijar VS 2022, hay que
  usar `windows-2022` con `-G "Visual Studio 17 2022"`.
- **Warnings de upstream**:
  - con MSVC, C4244 y C4324 en `psprecomp_core`;
  - con Clang, `-Wsign-conversion` en `include/psprecomp/common.hpp:18` (`out[9 - i]`).
  - Son inofensivos y quedan como **candidatos a parche upstream** (un `static_cast` explícito).
    No se tocaron.
- El framework de upstream pide CMake ≥ 3.20 y nosotros ≥ 3.22 (`CLAUDE.md`). En local se probó con
  CMake 4.4.
- **Entorno local**: `cmake`, `ninja`, `clang`, `ccache` y `clang-format` no están instalados en el
  sistema. En esta sesión se usaron desde un venv y `.deb` extraídos en el scratchpad. Para la
  próxima conviene instalarlos:
  `sudo apt-get install -y cmake ninja-build clang lld ccache clang-format`.
- El CI todavía no usa ccache. Hará falta cuando exista el código generado (F07).
- Las actions se subieron a `checkout@v7` y `setup-python@v7` para quitar el aviso de deprecación de
  Node 20.
